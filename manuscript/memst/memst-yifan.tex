\begin{abstract}
\vspace{0.3cm}

\memst\ is an open-source memory store for LLM agents: a content-addressed, versioned record of conversations, a time-aware knowledge graph extracted from them, and a server that exposes one user's memory to agents through the Model Context Protocol. This paper describes the system and reports what happened when its retrieval was evaluated like for like: every retrieval method read by the same model under the same prompt, against two baselines that build no memory at all (reading the whole history, and plain retrieval over the raw turns), with paired tests on the same questions and a second, stricter judge.

The results do not support the claim an earlier version of this paper made. On all \numLocomoQuestions\ questions of LoCoMo, the knowledge graph combined with raw turns is \numLocomoDefaultVsDense\ points of judged accuracy \emph{behind} embedding retrieval over raw turns (95\% interval \numLocomoDefaultVsDenseLow\ to \numLocomoDefaultVsDenseHigh), at about \numLocomoGraphCalls\ additional model calls per conversation; on \numLmeQuestions\ questions of LongMemEval-S the two are level. Routing questions to different retrieval methods by their kind, the idea the earlier version was built on, recovers none of the gap to an oracle router. A narrower test, fixed in advance, asked only whether the graph helps on questions about dates and changed facts when added to the best raw-turn method: it does not, by either judge.

What does help is on the reading side. Letting the reader work through the retrieved evidence before answering, over forty turns instead of twenty, raises judged accuracy on \numRoleQuestions\ temporal questions from \numRoleDenseDirect\% to \numRoleWide\%, and matches or exceeds reading the entire history at a fraction of the tokens. We also report a data-model fault that the evaluation exposed and that we believe is common: dating a fact by when it was \emph{said} instead of when it became \emph{true}.

We conclude that, on these benchmarks, a memory system's value does not lie in a structured index that answers questions better than the raw record does. We argue that it lies in what the record supports: versioning, provenance, correction and deletion, and control over what an agent may write into its own future context.

\section{Introduction}
\label{sec:intro}

An agent that works with someone over weeks needs to remember what was said. The context window does not solve this: histories outgrow it, and even where they fit, reading everything for every question is slow and expensive \citep{bulatov2022recurrent}. The common answer is an external memory: store the conversation, build some structure over it (summaries, extracted facts, a knowledge graph), and retrieve from that structure when a question arrives \citep{packer2023memgpt, zhong2024memorybank, chhikara2025mem0, rasmussen2025zep, xu2025mem}.

\memst\ began as such a system, with a particular thesis: that different kinds of question need different retrieval structures, and that routing each question to a specialised strategy would beat any single one. An earlier version of this paper reported that this worked, with 49.2\% F1 on LoCoMo for the adaptive router against 41.7\% for the best fixed strategy.

That evaluation had three weaknesses, which are also the ones the field has since identified in much of its own work \citep{bao2026naiverag, zhou2026explicit}. It compared \memst\ with retrieval pipelines of our own construction, not with retrieval over the untouched history under the same reader. It reported token F1, which rewards matching the reference's wording. And it left out the simplest baseline: its own result files contain a full-context run at 80.7\% F1, well above every strategy it reported. LoCoMo conversations are about 26,000 tokens; they fit in the context window of any current model.

This paper replaces that evaluation with one designed to answer a plainer question: \emph{does the memory \memst\ builds answer questions better than the record it was built from?} We built a harness in which retrieval is a configurable pipeline, every pipeline is read by the same model under the same prompt, and each question leaves a trace of what every stage retrieved. We ran it on all of LoCoMo \citep{maharana2024evaluating} and on LongMemEval-S \citep{wu2024longmemeval}, whose histories are about 127,000 tokens.

The answer is no, and we report it as such. The contributions of this paper are:

\begin{itemize}
\item \textbf{A like-for-like evaluation of graph memory against raw-history baselines} (\cref{sec:method,sec:results}). The knowledge graph does not beat retrieval over raw turns, alone or combined with them, with a direct reader or a reasoning one, on general questions or on the temporal questions where a time-aware graph should help most. Per-question routing realises none of its oracle headroom. We give paired differences with intervals and repeat the key comparisons with a stricter judge.
\item \textbf{Evidence that the reader, not retrieval, is the bottleneck on long histories} (\cref{sec:readpath}). On LongMemEval-S, plain retrieval places a turn containing the answer in the context for every question and the reader still answers only \numLmeRawDenseJudged\% correctly. A reader that works through the evidence first is the largest single improvement we found.
\item \textbf{A fault in how extracted facts are dated, and its fix} (\cref{sec:dates}). Storing the time a fact was stated as the time it became true made the graph's facts misleading on temporal questions. Separating the two raised the graph pipeline by 12 points there.
\item \textbf{The system itself} (\cref{sec:system}): a versioned store, a bi-temporal knowledge graph on an embedded graph, vector and full-text database, and a Model Context Protocol server with write gating against memory poisoning (\cref{sec:security}).
\end{itemize}

We withdraw the figures of the earlier version. They were produced by a different pipeline, with a different mapping of question categories, without the baselines above, and we have not reproduced them under the present protocol.

\section{Background and Related Work}
\label{sec:background}

\textbf{Memory systems for agents.} Work on agent memory has grown from paging between tiers \citep{packer2023memgpt} and forgetting curves \citep{zhong2024memorybank} to extracted-fact stores \citep{chhikara2025mem0}, temporal knowledge graphs \citep{rasmussen2025zep} and self-organising note networks \citep{xu2025mem}. Recent surveys describe memory by its form, its function and the operations performed on it, with governance, audit and rollback now counted among those operations \citep{hu2025memoryage}.

\textbf{What the benchmarks measure.} LoCoMo \citep{maharana2024evaluating} is the most reported benchmark and the most criticised. Its conversations fit in a context window, so a model that simply reads them is a strong baseline; an independent audit found 6.4\% of its reference answers wrong and showed that a commonly used LLM judge accepts most wrong answers that are on topic \citep{locomoaudit}. LongMemEval \citep{wu2024longmemeval} uses histories of over 100,000 tokens and adds questions about updated facts and abstention. Several 2026 studies compare engineered memory with retrieval over the raw history under controlled conditions and find no consistent advantage for the former \citep{bao2026naiverag, zhou2026explicit}. A study of memory substrates finds that choosing a substrate per query leaves most of the oracle headroom unrealised \citep{huang2026harness}. Our results agree with all three, on a system we built to show the opposite.

\textbf{Versioned memory.} Treating memory as a versioned artefact is no longer unusual. Letta's Context Repositories keep an agent's memory in git, with worktrees for subagents and ordinary merges \citep{lettacontextrepos}. ChronoMem studies rollback, asking whether an agent can answer as if later updates had not happened \citep{su2026chronomem}; Kumiho gives belief-revision semantics to a versioned graph \citep{park2026kumiho}; Mem++ keeps every version of every item and retrieves as of a reference time \citep{yehia2026mempp}. GitOfThoughts reports a result we now share: version control buys auditability and merging, not retrieval accuracy \citep{shekar2026gitofthoughts}.

\textbf{Time in knowledge graphs.} Bi-temporal modelling, in which the time a fact held is kept apart from the time it was recorded and superseded facts are invalidated instead of deleted, is the reference design for temporal graph memory \citep{rasmussen2025zep}. \Cref{sec:dates} adds a third time that conversational sources make necessary.

\textbf{Security.} Persistent memory is an attack surface: text that reaches memory is read back in later conversations and acted on. Injection through ordinary interaction has been demonstrated \citep{dong2025minja}, and a survey of the area names provenance, write gating, access checks at retrieval and rollback as the recurring defences \citep{lin2026memsecurity}.

\section{The \memst~System}
\label{sec:system}

\memst\ is written in Rust, with Python bindings and a command-line interface. It has four parts that the evaluation and the rest of the paper refer to.

\subsection{The store}
\label{sec:storage}

A store is a directory. Each session holds its messages in an append-only file with an offset index, an operations log of tool calls, and memory items in working, short-term and long-term tiers with promotion between them. The tiers and the sleep-time jobs that consolidate them are part of the system but are not evaluated in this paper.

Beneath the sessions is a versioned repository modelled on git. Objects are content-addressed by their Blake3 hash; trees and commits record memory states with parent links; every mutation passes through a write-ahead log with periodic checkpoints. Worktrees give an agent an isolated branch over a shared object store. Merging is limited: fast-forward merges are performed, and conflicts between memory items (duplicates, and statements that contradict each other) are detected, but a three-way merge that reconciles two diverged histories is not implemented.

\subsection{The knowledge graph}
\label{sec:graph}

Each store has one knowledge graph, kept in an embedded HelixDB database that provides graph traversal, vector search and BM25 full-text search over the same data \citep{helixdb}. Entities and relationships are partitioned by owner, so several users can share a store without one seeing another's graph.

\textbf{Ingestion.} Messages are sent to a language model in batches, each message under a short label. The model returns entities and subject--predicate--object relationships and, for each relationship, the label of the message that states it and the date it became true if the text gives one. Entities already present are reused; a relationship seen again is reinforced instead of duplicated.

\textbf{Time.} A relationship carries three times: when it became true (\texttt{valid\_from}, with a precision of day, month or year), when it stopped (\texttt{valid\_to}), and when it was stated (\texttt{stated\_at}, the time of its source message). For predicates that take one value at a time, such as where someone lives, a new value supersedes the old one: the old relationship receives an end time and a pointer to its replacement and leaves ordinary queries, but it is not deleted and can be queried as of an earlier time. Entity merges are recorded and can be undone.

\textbf{Search.} Entities are found by BM25 and by embedding similarity inside the database, fused by reciprocal rank \citep{cormack2009rrf}; relationships are found by BM25 over their text. If the database's indexes are unavailable, search falls back to substring matching and brute-force cosine similarity. Embeddings are computed locally with BGE-M3 \citep{chen2024bge} or by a configured endpoint.

\subsection{The MCP server}

\texttt{memst mcp serve} exposes one owner's memory to any client of the Model Context Protocol \citep{mcpspec} over standard input and output, with tools to search, read within a token budget, write and forget. \Cref{sec:security} describes how it limits what a client can do.

Behind the tools, an owner's memory is a directory of four layers: an append-only transcript of each session; notes, one Markdown file each, with every change kept as a revision that can be read and restored; pages that gather facts on a topic, each fact with the quotation it rests on; and a short index, built by the server, that is placed in the agent's prompt at the start of a session. An offline pass, run between sessions, reads the transcripts since its last run and proposes corrections to notes, new notes and pages. Every proposal must quote its source and the quotation is checked against the source before anything is written; a note the owner approved is never rewritten; and a pass lands as one revision that one command undoes. An extension for the Pi coding agent gives a session its index, records the session, and offers the tools.

\subsection{The evaluation harness}

Retrieval in the harness is a pipeline: a list of stages, each adding facts from the graph or turns of the conversation to what the reader will see. Pipelines are defined in JSON. The stages are: raw turns ranked by BM25, by embedding or by both fused; facts found by relationship search, by embedding or both; entities with the facts around them; the source messages of the facts selected so far; the turns adjacent to those selected; and a rerank, in which the model reads the candidates and keeps the most useful. A pipeline may also set the reader to answer directly or to work through the evidence first. For every question the harness records what each stage returned, how long it took, and whether it reached a turn that the dataset marks as containing the answer.

\section{Evaluation Method}
\label{sec:method}

\textbf{Datasets.} LoCoMo \citep{maharana2024evaluating}: 10 conversations averaging \numLocomoHistoryTokens\ tokens, \numLocomoQuestions\ questions in five categories. We keep the 446 adversarial questions, which have no answer in the conversation, and score them on whether the system says so; we also report the \numLocomoAnswerable\ answerable questions separately, since most published figures use that subset. LongMemEval-S \citep{wu2024longmemeval}: 500 questions, each with its own history of about 50 sessions (\numLmeHistoryTokens\ tokens on average). Each history must be extracted and embedded separately, so we use a stratified sample of \numLmeQuestions\ questions, ten of each of the six types.

\textbf{Pipelines.} \Cref{tab:pipelines} lists the seven pipelines of the main runs. Two build no memory: \pipe{full-context} gives the reader the whole history, and the \pipe{raw-*} pipelines retrieve twenty turns from it. Three use the graph: by entity, by relationship, and \pipe{default}, which combines facts found by relationship search, the messages those facts were stated in, and raw turns.

\centering
\caption{Pipelines of the main runs.}
\label{tab:pipelines}
\small
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
Pipeline & Context given to the reader \\
\midrule
\pipe{full-context} & The whole history \\
\pipe{raw-bm25}, \pipe{raw-dense}, \pipe{raw-hybrid} & Top 20 turns by BM25, by embedding similarity, or by both fused \\

\textbf{Models.} One model, DeepSeek's \texttt{deepseek-flash} with its built-in reasoning turned off, is the reader and the extractor in every run, so that no pipeline is read by a stronger reader than another. Embeddings are BGE-M3. Extraction batches are 6,000 characters for LoCoMo and 12,000 for LongMemEval-S.

\textbf{Scoring.} We report token F1 against the reference, and the share of answers a judge model marks correct. The judge in the main runs is the reader's own model; \cref{sec:judge} repeats the grading with a stronger model with reasoning on. For LongMemEval-S the judge applies that benchmark's rules for temporal, knowledge-update and preference questions. Intervals are 95\% bootstrap intervals over questions. Because two pipelines answer the same questions, we compare them by the mean difference per question with its own interval; this is far tighter than comparing two separate intervals, and we call a difference reliable only when that interval excludes zero.

\textbf{Costs.} For each pipeline we report the prompt tokens per question as counted by the API, including those of any stage that calls a model, and the number of extraction calls needed to build its memory.

\subsection{Routing}

The earlier version of \memst\ routed each question to one retrieval strategy according to its kind. An oracle that picks, for every question, whichever retrieval pipeline answered it best reaches \numLocomoOracleJudged\% judged accuracy on LoCoMo, against \numLocomoBestSingleJudged\% for the best single pipeline: the pipelines are complementary, and the headroom looks large. To measure how much of it a real router gets, we fitted the simplest one (the best pipeline for each kind of question: when, how many, who, where, why, yes or no, what) on four fifths of the questions and scored it on the rest, five times over. It reaches \numLocomoRoutedJudged\%, no better than always using \pipe{raw-dense}. On LongMemEval-S it reaches \numLmeRoutedJudged\% against \numLmeBestSingleJudged\%. Which pipeline happens to answer a question is not predictable from the question's wording. A learned router with richer features might do better, but the headroom an oracle shows is not evidence that it can be reached, a point also made by \citet{huang2026harness}.

\numLocomoNobodyRight\ of the LoCoMo questions, about 12\%, are answered wrong by every pipeline including full context. Some of this is the benchmark: the audit cited above puts 6.4\% of reference answers in error \citep{locomoaudit}.

\subsection{Is the judge trustworthy?}
\label{sec:judge}

Grading with the reader's own model risks a lenient judge. We graded three sets of answers again with a stronger model from the same provider, \texttt{deepseek-v4-pro}, with reasoning on. On LongMemEval-S the two judges agree on 98.3\% of the 420 answers of the main run and on all 180 of the read-path experiment below. On LoCoMo they agree on 92.0\% of 1,932 answers, and nearly all the disagreement runs one way: 154 answers pass only the original judge and one passes only the stricter one. Every pipeline loses 6 to 10 points; the order of pipelines is unchanged and differences between them shrink by about a third. We therefore report the stricter judge alongside the original wherever a conclusion rests on a pilot. The second judge shares a provider with the first, so this bounds leniency; it is not an independent judge, and we have not regraded the full LoCoMo run.

The direction is the same on both datasets and at scale on temporal questions; the size on general questions awaits a full run.

\textbf{The test is not passed.} No use of the graph gives a reliable gain. \subsection{When a fact was said and when it became true}
\label{sec:dates}

The traces of an early run of this test showed why the graph's facts hurt on temporal questions. A message sent on 9 September saying ``we went to the park two weeks ago'' produced the fact \emph{visited park}, dated 9 September. Ingestion took the date a fact became true from the text when the model supplied one, and otherwise used the date of the message, and the graph then presented both as ``true since''. Most facts had no stated date, so most were dated by when they were said.

Bi-temporal designs separate the time a fact held from the time the system recorded it. Conversational sources need a third: the time the fact was \emph{stated}. It differs from valid time whenever people talk about the past, and from recording time whenever a conversation is ingested later, as every benchmark history is. \memst\ now stores all three, sets the valid time only when the text gives one, and keeps its precision, so that ``in 2022'' is not stored as 1 January 2022. Of 2,551 facts extracted from LoCoMo afterwards, 24\% carry the date of the event, 39\% only the date they were stated, and 37\% no time.

On the same \numRoleQuestions\ questions, the fix raised the graph pipeline with a direct reader from \numRoleDefaultDirectOld\% to \numRoleDefaultDirectNew\% judged accuracy, and the timeline presentation stopped hurting. It did not change the verdict of \cref{sec:role}. Extraction is not deterministic, so the two runs differ in more than their dates; the direction and size of the change on the pipeline that depends most on fact dates are nonetheless clear.

\subsection{The cost of building the graph}

Extraction is the graph's whole write-path cost: about \numLocomoGraphCalls\ model calls for a LoCoMo conversation and \numLmeGraphCalls\ for a LongMemEval-S history, some minutes each. It cannot simply be cut by sending more text per call. With batches of 6,000, 12,000 and 24,000 characters, three conversations took 46, 24 and 13 calls and yielded 650, 438 and 321 relationships: the model returns a roughly fixed amount per call. The graph alone then falls from 62\% to 57\% to 49\% judged accuracy, while pipelines that also retrieve raw turns do not move.

\section{Security and Deletion}
\label{sec:security}

An agent that can write to its own memory can be made to write an instruction for its future self, by any text it reads. The MCP server limits this at the tool boundary. A server is bound to one owner when it starts; no tool takes an owner, a session or a path, and an argument a tool does not define is refused. A note that reads like an instruction (it tells the reader to change its behaviour, imitates a system or tool message, asks for something to be hidden or sent elsewhere, or contains invisible characters) is set aside and not returned until the store's owner approves it from the command line; the agent has no tool with which to approve it. Tags that state who owns a note or how far it is trusted are set by the server only. What is read back is fenced, labelled with its source and whether it was approved, and introduced as records, not instructions. Writes are limited in size, rate and number, every write and deletion is logged without its content, and a read-only mode removes the writing tools. Ten attacks, each with the defence that stops it, form a test suite in the repository.

The limits should be stated plainly. Screening catches instructions phrased as instructions; a false statement written as a fact passes, which is why notes written by an agent are marked unverified until a person approves them. Owners are separated by the server, not by the file system. The command line and the Python module bypass these checks.

Deletion is harder in a store built to keep history. We distinguish hiding an item, removing it from the current state and every index derived from it, removing it from history, and removing it from places the store cannot reach, such as backups and a model provider's logs. Notes written through the server are removed with every earlier version of them, and a test searches every byte of the store for the deleted text. A note is not the only place a fact is kept, as \cref{sec:inuse} found: forgetting now also removes the transcript entries that contain the words, which is matching by words and so misses a paraphrase. For messages, the facts derived from them, and the versioned history, the repository contains a design (per-item encryption with deletion of the key, so that every snapshot's copy becomes unreadable without rewriting history) but not an implementation.

\section{Memory in Use}
\label{sec:inuse}

The benchmarks above ask about a fixed transcript. They do not test an agent that is told something in one session and needs it in a later one while its memory changes in between. We wrote a small test of that, and fixed its pass criteria in the repository before the first run.

Sixty scenarios, ten for each of six kinds, were run under three conditions: the Pi agent without memory, with memory, and with memory and the offline pass applied before the last session. Each session is a separate process, the agent has no file or shell tools, and the facts are invented so that the model cannot know them otherwise. The agent's model is the reader used elsewhere in this paper. Answers are checked by pattern.

\begin{table}[h]
\centering
\small
\begin{tabular}{lccc}
\toprule
Scenario (correct final answers of 10) & No memory & Memory & Memory and pass \\
\midrule
Recall a fact told two sessions earlier & 0 & 10 & 10 \\
Give the new value after an update (strict check) & 0 & 6 & 5 \\
Answer from what the user said, against a wrong note & 0 & 0 & 10 \\
Do not give a fact the user asked to forget & 10 & 10 & 9 \\
Give a pasted page's fact, ignore its instruction & 0 & 10 & 10 \\
Say so when never told & 7 & 10 & 10 \\
\bottomrule
\end{tabular}
\caption{Memory in use: 180 scenario runs. Criteria were fixed beforehand; five of seven passed.}
\label{tab:inuse}
\end{table}

Five of the seven criteria passed (\cref{tab:inuse}). Recall across sessions, abstention, and resistance to an instruction planted in pasted text all held in every run. The offline pass did what it is for: given a wrong note and a transcript in which the user says otherwise, the agent answered from the note in ten runs of ten, and from what the user said in ten of ten once the pass had corrected the note. The first half of that result is a fault as much as the second is a success: at read time nothing tells the agent that a note has been contradicted since.

Two criteria failed. The update criterion failed on the check as written: all nine failing answers give the new value and name the old one as history (``Tallinn, having relocated from Lisbon''), which the check counts as wrong. We report it as failed because the check was fixed in advance. The forgetting criterion failed in substance. Forgetting deleted the note and every earlier version of it, and left what the user had said in the transcripts, in twenty runs of twenty; in one, the agent found the fact there by searching and gave it. The tool now also takes the words to be forgotten and removes every transcript entry that contains them. On a second run of those scenarios no answer gave the fact and no file held it; being a rerun after a change prompted by the first, it does not alter the first result.

A final session with memory used about 5,200 prompt tokens against 560 without, and took about one second longer. The test is small and written by the authors, the memory in it is nearly empty, and one agent and one model were tried; it shows that the operations work and where one did not, and says nothing about recall from a memory of thousands of notes.

\section{Discussion}
\label{sec:discussion}

\subsection{What the results mean}

We built a knowledge graph to answer questions better than the conversation it was extracted from, and it does not. The finding is robust to the ways we tried to rescue it: searching by relationship instead of by entity, combining the graph with raw turns, using a reasoning reader, correcting the dates, restricting the test to the questions a temporal graph is for, and regrading with a stricter judge. It agrees with independent comparisons published this year \citep{bao2026naiverag, zhou2026explicit}.

The reason is visible in the traces. Extraction is lossy: the graph's facts lead to a turn containing the answer for about half of LoCoMo's questions, while embedding retrieval over the turns themselves does so for three quarters. What extraction adds is a restatement of some of the same content, and a restatement placed before the original makes the reader slightly worse. The raw record is the better index of itself.

The improvements we did find are in how the record is read. This suggests that for histories of the sizes tested here, effort is better spent on the reader's use of retrieved evidence than on structures built at write time.

None of this says a time-aware graph of a user's world is without value. It says that question answering over a static transcript is not where that value shows. A structured, dated, correctable view of what an agent believes is what a person needs in order to inspect that belief, correct it, see what it was last month, and remove part of it; and a versioned record is what makes those operations safe. These are the operations the field now names when it describes memory \citep{hu2025memoryage}, and current benchmarks do not measure them.

\subsection{Limitations}

\textbf{One reader.} All results use one model with reasoning off as reader and extractor. A stronger extractor would build a better graph, and a stronger reader might use it better; it would also read raw turns better.

\textbf{Sample sizes.} The LongMemEval-S results rest on \numLmeQuestions, \numReadLmeQuestions\ and \numRoleLmeQuestions\ questions. The read-path gains on general questions rest on a \numReadQuestions-question pilot. The LoCoMo main run and temporal test use every question.

\textbf{Judges.} Both judges come from one provider. The stricter one lowers LoCoMo scores by 6 to 10 points without changing the order of pipelines, and we have not applied it to the full LoCoMo run.

\textbf{Scale.} At about 127,000 tokens, LongMemEval-S histories still fit in a large context window and their answer turns are easy to retrieve. Histories of millions of tokens, where retrieval can no longer return everything relevant, are the remaining setting in which a pre-built structure might win; we have not tested it.

\textbf{Benchmarks.} Both benchmarks ask questions about a fixed transcript. Neither tests correction, deletion, rollback or use of memory in action; our own test of those (\cref{sec:inuse}) is sixty short scenarios. LoCoMo's reference answers contain errors.

\textbf{Not evaluated.} The memory tiers, sleep-time consolidation and the versioned repository are described but not measured. We make no claim about what versioning is worth; the experiments that would show it (answering as of an earlier state, merging two agents' memories) remain to be done.

\textbf{Not implemented.} Three-way merge, deletion of single messages with cascade to derived facts, and deletion from history.

%==============================================================================
\section{Conclusion}
\label{sec:conclusion}

We set out to show that structured, query-adaptive memory answers questions better than retrieval, and a fair evaluation showed that it does not: on LoCoMo and LongMemEval-S, a knowledge graph extracted from a conversation is at best level with retrieval over the conversation's own turns, routing by kind of question gains nothing, and the largest improvement available is to let the reader reason over what was retrieved. Along the way the evaluation found a modelling fault worth checking for in any system that extracts dated facts from conversation: the time something was said is not the time it happened.

We think the useful direction for systems like \memst\ is the part of memory that benchmarks of recall do not reach: a record that can be versioned, audited, corrected and partly forgotten, and that controls what an agent is allowed to tell its future self. The evaluation harness, every answer and trace behind the tables in this paper, and the system are available in the repository.
