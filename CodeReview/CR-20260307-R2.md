## Medium Issues

### Issue M1: Incomplete LLM Integration

**Location:** `memst-extract-v2/src/extraction.rs:64-93`

**Current Code:**
```rust
pub async fn extract_entities(
    &self,
    doc_id: &str,
    _text: &str,  // Text is ignored!
    ontology_id: &str,
) -> Result<ExtractionJob> {
    let job_id = format!("job-{}", Uuid::new_v4());
    let now = Utc::now();
    
    let job = ExtractionJob {
        id: job_id,
        doc_id: doc_id.to_string(),
        ontology_id: ontology_id.to_string(),
        status: ExtractionStatus::Completed,  // Always completed
        started_at: now,
        completed_at: Some(now),
        error_message: None,
        entity_count: 0,     // Always 0
        relationship_count: 0,
        argument_count: 0,
        llm_calls: 1,        // Faked
        tokens_used: 0,
    };
    
    self.storage.store_extraction_job(&job)?;
    Ok(job)
}
```

**Issue:** The `extract_entities` method is a placeholder that:
1. Ignores the input text (`_text` parameter prefixed with underscore)
2. Returns immediately with empty results
3. Fakes LLM call count without making any LLM calls
4. Always returns `Completed` status

**Impact:** The extraction pipeline is non-functional for actual entity extraction. This is a skeleton implementation.

**Recommendation:**
1. Integrate with `PromptEngine` to generate extraction prompts
2. Call LLM provider (e.g., `async-openai`) to process text
3. Parse LLM response to extract entities
4. Store extracted entities in database
5. Update job status properly based on actual results

**Priority:** High (before production use)

### Issue M4: In-Memory Storage Uses Temp Files

**Location:** `memst-extract-v2/src/storage/sqlite.rs:47-60`

**Current Code:**
```rust
pub async fn new_in_memory() -> Result<Self> {
    // For in-memory, we'll use a temporary file to allow multiple connections
    let temp_dir = std::env::temp_dir();
    let db_path = temp_dir.join(format!("memst_extraction_{}.db", uuid::Uuid::new_v4()));
    // ...
}
```

**Issue:** "In-memory" storage actually creates temporary files on disk. This:
1. Leaves orphaned files in `/tmp` if not cleaned up
2. May expose sensitive data in temp directory
3. Doesn't truly provide in-memory performance

**Recommendation:** Use proper SQLite in-memory mode:
```rust
// For true in-memory (single connection)
Connection::open(":memory:")

// Or use shared cache for multiple connections
Connection::open("file::memory:?cache=shared")
```

### Q2: StorageConfig Default Backend Logic

**Location:** `memst-extract-v2/src/lib.rs:43-62`

**Issue:** The `sqlite()` constructor has confusing fallback logic:
```rust
pub fn sqlite<P: AsRef<Path>>(path: P) -> Self {
    Self {
        #[cfg(feature = "sqlite")]
        backend: BackendType::Sqlite,
        #[cfg(not(feature = "sqlite"))]  // Fallback when sqlite disabled
        backend: BackendType::DuckDb,    // But this won't compile!
        // ...
    }
}
```

If SQLite feature is disabled, it tries to use `DuckDb` variant which may not exist either.

**Recommendation:** Use compile-time error instead:
```rust
#[cfg(not(feature = "sqlite"))]
compile_error!("SQLite feature must be enabled to use StorageConfig::sqlite()");
```
